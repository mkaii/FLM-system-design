SHEET 05

The 8 user actions, from the Problem Statement

  1. Browse movies.
  2. Browse theatres and screens.
  3. View shows for a movie.
  4. View seats for a particular show.
  5. Select seats.
  6. Temporarily lock selected seats.
  7. Complete payment.
  8. Confirm a booking.

The spec's own suggested API list has no endpoint for action 2 — browsing theatres and screens. It's called out honestly below on each card rather than papered over: as written, a client can jump straight from "browse movies" to "view shows for a movie" without ever listing theatres, which is fine for a single-theatre-per-city demo but worth noticing before assuming the API list is complete.

  }

ShowController → ShowService → ShowRepository (filtered by movieId)

GET /shows/{showId}/seats

Covers action 4 — view seats for a particular show. Example straight from the spec.

Input

path: showId
e.g. GET /shows/101/seats

Output — 200

[
  {
    "seatNumber": "A1",
    "type": "REGULAR",
    "status": "AVAILABLE"
  },
  {
    "seatNumber": "A2",
    "type": "PREMIUM",
    "status": "BOOKED"
  }
]

ShowController → ShowService → Show's own Map<SeatId, ShowSeat> (read directly — no repository call, since ShowSeats live inside the Show, not in a separate store)

POST /bookings/lock

Covers actions 5 & 6 — the client has already selected seats; this call is what turns that selection into a real, held lock.

Input — body

{
  "showId": "show101",
  "seatIds": ["A1", "A2"],
  "userId": "u1"
}

Output — 200

{
  "bookingId": "b1",
  "status": "PENDING",
  "lockedSeats": ["A1", "A2"],
  "lockExpiresAt": "...",
  "totalAmount": 500
}

BookingController → BookingService → SeatLockManager (per-seat lock) → ShowSeat.lock() → PricingStrategy.calculatePrice() → BookingRepository (creates PENDING booking)

POST /bookings/{bookingId}/pay

Covers action 7 — complete payment.

Input

path: bookingId
body: { "paymentMethod": "CARD" }

Output — 200

{
  "bookingId": "b1",
  "paymentStatus": "SUCCESS"
}

BookingController → BookingService → PaymentStrategy.pay(amount) → BookingRepository (records payment result; on failure, releases locked seats — see Booking Flow, Branch A)

POST /bookings/{bookingId}/confirm

Covers action 8 — confirm a booking.

Input

path: bookingId

Output — 200

{
  "bookingId": "b1",
  "status": "CONFIRMED",
  "seats": ["A1", "A2"]
}

BookingController → BookingService → ShowSeat.book() per locked seat → BookingRepository (status → CONFIRMED)

GET /bookings/{bookingId}

Not one of the 8 numbered actions directly — supporting read, used e.g. to poll status after payment or while a lock is still counting down.

Input

path: bookingId

Output — 200

{
  "bookingId": "b1",
  "status": "PENDING",
  "seats": ["A1", "A2"],
  "totalAmount": 500,
  "createdAt": "..."
}

BookingController → BookingService → BookingRepository

SHEET 05

Error cases — spec wording, plus proposed status codes

CaseSpec saysProposed status
Seat already booked Reject the booking attempt. 409 Conflict
Seat already locked Reject the booking attempt if another user owns the lock. 409 Conflict
Lock expired The seat should become available. 410 Gone
Payment failure Release the locked seats. 402 Payment Required
Invalid state transition Prevent transitions such as BOOKED → AVAILABLE through normal booking operations. 409 Conflict

The left two columns are quoted from the spec's own "Error Cases" section. The status codes are proposed, not spec-mandated — the spec describes required behavior (reject, release, prevent) but never names an HTTP status. 402 is a semantically fitting but unusual choice for a REST API in practice; 400 Bad Request is a defensible substitute if consistency with the rest of a team's existing API conventions matters more than semantic precision.
