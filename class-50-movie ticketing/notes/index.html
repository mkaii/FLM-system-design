System Overview

A BookMyShow-style booking system, built as an LLD exercise: plain-Java domain and business logic, Spring Boot only as the web layer. The one hard requirement running through everything below: two users racing for the same seat on the same show — exactly one of them wins.

SHEET 00

Package structure

movie-booking/
├── controller/  thin — parse request, call one service method, return response
├── domain/      Movie, Theatre, Screen, Seat, Show, ShowSeat, Booking, User, Payment
├── service/     MovieService, ShowService, BookingService, PaymentService
├── repository/  interfaces + InMemory* implementations
├── pricing/     PricingStrategy + Regular/Weekend/Holiday
├── payment/     PaymentStrategy + Mock/Card/UPI
├── locking/     SeatLockManager, per-ShowSeat ReentrantLock registry
├── state/       SeatState + Available/Locked/Booked
├── exception/
└── test/       including the 100-thread concurrent-booking test

Only controller/ may depend on Spring. Everything else must be pluggable, constructor-injected, plain Java — testable without a Spring context at all.

SHEET 00

Build order (10 phases)

  1. Domain model — the 9 classes and their relationships, no Spring, no persistence.
  2. Repository interfaces + in-memory implementations.
  3. Basic services — Movie, Show, Booking, Payment — plain Java.
  4. Pricing strategy — Regular / Weekend / Holiday.
  5. Seat state — start with an enum, replace with the State pattern once the design justifies it.
  6. Temporary seat locking — SeatLockManager, configurable expiry.
  7. Thread safety — per-ShowSeat ReentrantLock, atomic check-then-act.
  8. Concurrent tests — many threads racing one seat, exactly one winner.
  9. Spring Boot REST APIs — thin controllers over the already-working core.
  10. Design review — SOLID, DRY, encapsulation, extensibility, error handling.

Note the order: State (5) and locking (6–7) come before Spring Boot (9). The instruction is explicit — do not generate the whole project at once, and do not reach for Spring until the plain-Java core already works and is tested.

SHEET 00

The 13 questions this design has to survive

  1. Why is Show separate from Movie and Screen?
  2. Why does ShowSeat exist at all?
  3. Why is availability stored on ShowSeat instead of Seat?
  4. How does pricing stay extensible?
  5. Why use the Strategy pattern for it?
  6. When would the State pattern actually be useful here?
  7. How is double booking prevented?
  8. Why per-seat locking instead of one global lock?
  9. What role does ConcurrentHashMap actually play?
  10. What happens when payment fails?
  11. What happens when a seat lock expires?
  12. What changes with multiple Spring Boot instances?
  13. How would database locking or Redis change the design?

Every other sheet in this set exists to answer one or more of these. Questions 2–3, 7–9 are the load-bearing ones — get those wrong and the rest of the design doesn't hold up.
