Seat State

The spec is explicit that this is not a future refactoring — the State pattern must be present when seat state is first introduced. ShowSeat never runs an if/else on its own status; it asks its current SeatState object what to do, and that object either performs the transition or refuses it.

Legal vs. illegal transitions

Note the difference between ShowSeat.status (three values only: AVAILABLE / LOCKED / BOOKED) and Booking.status (PENDING / CONFIRMED / CANCELLED / EXPIRED) — these are two separate state machines on two separate classes. A lock timing out is a ShowSeat event (release(), back to AVAILABLE); a booking timing out is a Booking event (its own status moving to EXPIRED). Don't reach for a shared "expired" concept across both — they track different things.
