CLASS 71 - TEACHING NOTES: SSE and WebSocket
Use case all along: Swiggy. Order #7 is on its way. The customer wants to see where the rider is.


========================================================================
 PART 1: SSE (Server-Sent Events)
========================================================================

--- WHAT TO SAY (flashcards) ---

[1] The problem
    Normal HTTP: the app asks, the server answers, done.
    The server can never speak first. So how does the rider's new location reach the customer?

[2] SSE in one line
    The customer's app asks ONCE: "keep sending me updates".
    The server never finishes the answer. It keeps adding to it whenever there is news.

[3] Like a phone call
    You call, say one sentence ("tell me about order 7"), then just listen.
    The other side keeps talking whenever they have something new.

[4] Who calls what
    Customer app  ->  GET /events     once. This answer never ends.
    Rider app     ->  POST /send      every time the rider moves. A normal request.
    The server takes the rider's news and writes it into the customer's open answer.

[5] The server does NOT call the customer
    The customer's phone has no address the server can call.
    The server only writes into the answer of the request the customer already made.

[6] One way only
    Server -> customer: yes.  Customer -> server on the same line: no.
    If the customer wants to say "ring the bell", that needs a separate request.

[7] The special header
    Browser sends:  Accept: text/event-stream     ("keep the answer open, send me events")
    Server replies: Content-Type: text/event-stream

[8] "Stream" here is not a Redis Stream
    It just means data arriving bit by bit. Nothing is stored. Miss it, and it's gone.

[9] It reconnects by itself
    If the line drops, the browser opens it again automatically.

[10] Used for
    Live cricket score, stock prices, order status, AI answers typing out word by word (ChatGPT, Claude).

[11] Code, in two lines
    Server: return an SseEmitter (the open answer); call emitter.send("...") to add a message.
    Browser: new EventSource("/events"); onmessage runs for each message.
    No extra dependency: it's part of normal Spring web.

========================================================================
 PART 2: WebSocket
========================================================================

--- WHAT TO SAY (flashcards) ---

[1] What SSE couldn't do
    The customer wants to reply: "please ring the bell". SSE is one way. We need both ways.

[2] WebSocket in one line
    An always-open line where BOTH sides can send messages, any time.

[3] Like a phone call where both people talk
    SSE: you only listen.  WebSocket: you both talk, on the same call.

[4] Who connects
    Customer app and rider app each open ONE line to /chat, once.
    After that, nobody makes new requests. They just send messages on their open line.

[5] How the line opens
    It starts as a normal HTTP request saying "Upgrade: websocket".
    Server answers "101 Switching Protocols". From then on it's not HTTP any more: it's a two-way pipe.

[6] What the server does
    A message comes in on one person's line -> the server writes it into the other person's line.
    Rider -> customer and customer -> rider work exactly the same way.

[7] ws:// and wss://
    ws:// is like http://.  wss:// is the secure one, like https://.

[8] SSE vs WebSocket, in one line each
    SSE: one way (server -> customer), 2 APIs in our demo (/events to listen, /send to talk).
    WebSocket: both ways, 1 endpoint (/chat) for everyone.

[9] Used for
    Chat (WhatsApp Web, Slack), live location with replies, multiplayer games, Google Docs-style editing.

[10] Code, in three pieces
    ChatHandler: keeps the list of open lines; a message from one goes to everyone else.
    WebSocketConfig: just says "/chat -> ChatHandler" (the WebSocket version of @GetMapping).
    Browser: new WebSocket("ws://localhost:8081/chat"); onmessage to receive; ws.send(...) to send.
    Needs one extra dependency: spring-boot-starter-websocket.

    (class-71/websocket-demo) -> Tomcat started on port 8081

                                                                  Handler: pass each message to everyone else."

    -> console: CONNECTED: 1 people on /chat

    -> Connect -> console: CONNECTED: 2 people on /chat

    -> Postman Messages shows it                                  This is what SSE couldn't do."

 (Postman won't put a WebSocket request into a normal HTTP collection.)
